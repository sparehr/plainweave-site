How an audit runs

Your side of it is one approval and one review call.

You authorise read-only access

You see every permission and the reason for it before you approve. A connector is refused any permission you did not approve.

The agents read metadata first

Names, counts, timestamps and owners. Message and file content is read only if you grant it separately.

Each role maps its department

Every role that received records writes findings, each with citations.

The verifier checks every finding

Anything it cannot trace to a stored, unchanged source is rejected.

You get one report

A single page. Every line links to its evidence, and the page lists what was and was not examined.

How the agents work

Each agent takes one department and reads its systems. It writes down what it finds. A separate verifier checks every finding against the source and rejects anything it cannot prove.

  1. 01 · Your systems

    It can only read

    Plainweave connects to your systems with read-only access. It keeps counts, dates and owners, and drops message text and file contents before anything is stored.

    GitHubSlackGoogle Workspace
  2. 02 · Evidence ledger

    Records are sealed

    Every record is stored once, fingerprinted, in a database that belongs to your company alone. A stored record is never edited.

  3. 03 · Role-agents

    One role per department

    Each record goes to the agent for its department. The agent writes findings, and each finding must name the records it rests on.

  4. 04 · Verifier

    A different agent checks

    It re-reads every cited record. A finding whose evidence is missing, changed or does not hold the quoted value is rejected.

  5. 05 · Report

    Verified findings only

    The report holds verified findings and the records they cite. Nothing else leaves your database.

Rejected findings stay in your store with the reason. They never reach the report.

Every line has a source you can open.

A finding names the record it rests on and the exact field. The verifier re-reads that record. If the evidence is missing, changed or does not say what the finding claims, the finding is rejected and never reaches your report.

  • We found, never we believe. Anything unverified is labelled unverified or left out.
  • The role that writes a finding cannot verify it.
  • It reports queues, teams and handoffs. It does not judge individuals.

A citation is a record, the hash the author saw, a pointer to one field and the value expected there.

3 · The verifier checks it
  • The verifier is not the author
  • The finding cites at least one record
  • The record is in your store
  • Its hash still matches
  • The pointer resolves
  • The quoted value is there

These six checks are code, not a model. They prove the evidence exists and is unchanged. A second, model-based check of whether the claim follows from the evidence is built and is off by default.

Checks every finding

Verifier

Writes no findings. Re-reads every cited record and returns a verdict with reasons. It does not repair a finding.

  • Agents have no tools that act on your systems. A role reads stored records and writes findings. That is all it can do.
  • Text inside a record is treated as data, never as an instruction to the agent.
  • Routing is a fixed rule today. GitHub records go to Engineering; everything else goes to Operations. Model-assisted routing is not built.
  • Every model call is metered per role and per connector, and a run can carry a cost ceiling that stops it before the ceiling is passed.

Questions before you say yes

Short answers. The security page has the detail, including what is not in place.

Is this a tool our developers have to run?

No. It is an audit for whoever runs the company or its operations. Your side is one approval and one review call. What you get is a report you can read without a technical background.

Will it tell us how much we will save?

No. The report shows what is there: work that waits, queues with no owner, what you pay for, and a ranked list of what to fix. It does not estimate savings, because an estimate is not evidence.

Can Plainweave change anything in our systems?

No. Plainweave can only send read requests. There is no write, send or delete path in it, and the agents have no tools that act on your systems. The security page has the technical detail.

Does it read our messages and documents?

Not by default. Connectors keep metadata such as counts, timestamps and owners, and drop message text, titles and file bodies before anything is stored. Some permissions the providers offer would technically expose content; we mark those for you before you approve. Content is a separate grant for the engagement, and without it a content request is refused.

What exactly do we approve?

A list of every permission each connector requests, with the reason for each. Exact scopes are confirmed with you in writing before access is granted.

Where is our data kept?

In a separate database for your company, with no shared tables. Credentials are sealed in a vault outside that database, so a report or a backup never contains one. Only verified findings and the records they cite leave the store.

Can we stop it?

Yes. Revoke access from your own admin console at any time and collection stops.

Has this run at a real company?

Not yet. The pipeline is built and tested on fixtures for an invented company. The connectors have not read a live workspace, and no app is registered with GitHub, Slack or Google yet. Design partners are the first real audits.

What is not in place?

No SOC 2 report, no per-client encryption keys, no signed exports, and the data processing agreement is a draft. The security page keeps the full list.
